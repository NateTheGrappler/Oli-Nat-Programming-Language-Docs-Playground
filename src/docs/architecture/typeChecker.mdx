# Type Checker

Alright, so we have trees now. The AST compiler spent all of that effort building them, but so far nothing has actually asked whether they make any sense. `1 + "hello"` is a perfectly good tree, it just isn't a perfectly good *program*. That is where the type checker comes in. <br />

The type checker is what makes Oli-Nat a **statically typed** language. It walks through every tree that the [AST compiler](https://olinat.net/docs/system-design/astCompiler) builds and works out the type of each piece of it, and if anything doesn't line up, the program stops with an error **before a single line of it ever runs**. It is also one of the smaller parts of the pipeline, about 1100 lines, and roughly a fifth of that is just a list of standard library functions. <br />

Remember `expressionStatement()` from the AST Compiler page? Every expression gets passed to the type checker right after it is built, and the type that comes back decides whether we go on to compile it. <br />

This page is split into three parts, going from easiest to hardest. First, how a tree gets checked. Second, the symbol table, which is how the checker remembers things. And third, how that same table is used for functions, native functions, and classes. <br />

Before that though, here are the types themselves. Everything in the checker is built on this one enum:


You have seen most of these already. There are the basic types, the array version of each one, and `VALUE_CLASS` and `VALUE_INSTANCE`, which we will get to at the end. `VALUE_ERROR` is the checker's way of saying "this expression is broken". The three `VALUE_ANY` types at the bottom are special, and only exist for native functions. They are explained in part three.

# Checking Expressions

The whole job of the checker comes down to one function, `checkExpression()`. You give it a tree, and it gives you back the **type** that the tree evaluates to (or `VALUE_ERROR` if something is wrong). Here is the front of it:

```c++
ValueType checkExpression(TypeChecker* checker, Expr* expr, ASTparser* parser)
{
    //...
    if (expr == NULL) return VALUE_ERROR;


    ValueType result;
    switch (expr->type)
    {
        case EXPR_BINARY:
        {
            result = checkBinary(checker, expr, parser);
            break;
        }
        case EXPR_LITERAL:
        {
            result = checkLiteral(expr);
            break;
        }
        case EXPR_UNARY:
        {
            if (expr->unary.right == NULL)
            {
                return VALUE_ERROR;
            }
            result = checkUnary(checker, expr, parser);
            break;
        }
        case EXPR_GROUPING:
        {
            result = checkGrouping(checker, expr, parser);
            break;
        }
        case EXPR_VARIABLE:
        {
            result = checkVariable(checker, parser, expr);
            break;
        }
        //...
```

It is a big `switch` on the `type` of the expression, the same enum you saw on the AST page. Each case looks at one kind of node and decides what it evaluates to. Some cases are small enough to live right inside of the switch, and others call a helper function. <br />

The part that makes this work is **recursion**. To know the type of a node, we first need to know the type of everything underneath it, so every check calls `checkExpression()` on its children and then combines the answers. Types bubble up from the leaves of the tree to the root, which is the same order that the tree gets evaluated in. Let's start at the leaves:

```c++

    return expr->literal.type;
```

`checkLiteral()` is the base case, it doesn't recurse at all. Remember `number()` from the AST compiler? The literal was created with its type already attached (`createLiteralInt`, `createLiteralDouble`), so all the checker has to do is read it back. `checkGrouping()` just passes things along, since `(x)` has the same type as `x`. <br />

`checkUnary()` is the first one that recurses. It checks the expression on its right, and then looks at the operator. A `-` only works on numbers and gives back the same type it was given, and a `!` only works on booleans. Anything else is an error, and we return `VALUE_ERROR`. (A fun little detail is that unary operators are stored as a single `char`, where binary operators are whole strings.) <br />

Now for the beefy boy:

```c++

    ValueType leftType = checkExpression(checker, expr->binary.left, parser);
    const char* operator = expr->binary.operator; //it's a 2 char array so it's 2 bytes

        strcmp(operator, "-") == 0 ||
        strcmp(operator, "/") == 0 ||
        strcmp(operator, "*") == 0 )
    {
        if (isNumeric(leftType) && isNumeric(rightType)) return checkBinaryReturnType(rightType, leftType); //somehow handle different expression outputs
        if (strcmp(operator, "+") == 0 && rightType == VALUE_STRING && leftType == VALUE_STRING) { return VALUE_STRING; }

        typeError(checker, parser, expr, "If you want to do math, you have to use numbers (double, float, int), please." , "TYPE ERROR");
        return VALUE_ERROR;
    }

    //handle arithemtitec boolean operators
    if (strcmp(operator, "<") == 0 ||
        strcmp(operator, ">") == 0 ||
        strcmp(operator, "<=") == 0 ||
        strcmp(operator, ">=") == 0 )

        typeError(checker, parser, expr, "Operators comparing value must compare numbers only.", "TYPE ERROR"); //TODO: maybe add checking strings too idk
        return VALUE_ERROR;
```

*Found in /src/typeChecker.c*

`checkBinary()` checks both sides first, and then looks at the operator, using `strcmp`. This is where storing the operator as a string back on the AST page pays off. There are three families of operators: <br />

- **Arithmetic** (`+ - * /`): both sides have to be numbers, and the type of the result comes from `checkBinaryReturnType()` below. The one exception is `+`, which can also join two strings together.
- **Comparison** (`< > <= >=`): both sides have to be numbers, and the result is always a `bool`.
- **Equality** (`== !=`): both sides have to be the same type, or both be numbers. The result is always a `bool`.

```c++
static ValueType checkBinaryReturnType(ValueType right, ValueType left)
{
    //return same types, then float piority, otherwise it has to be a double
    if (right == left) return right;
    if ((right == VALUE_FLOAT && left == VALUE_INT) || (left == VALUE_FLOAT && right == VALUE_INT)) return VALUE_FLOAT;
    return VALUE_DOUBLE;
}
```
*Found in /src/typeChecker.c*

This is Oli-Nat's type promotion; if both sides are the same type, we get that type back, so `int + int` is an `int`. (That includes `5 / 2`, which is `2` and not `2.5`.) An `int` mixed with a `float` gives a `float`, and anything else has to involve a `double`, so we get a `double`. That makes `1 + 2.5` a `3.5`. <br />

*Cool Note:* Promotion only happens **inside** of an expression. When it comes to declaring or assigning a variable, the type has to match *exactly*, so `make int x = 1 + 2.5;` is an error, because `1 + 2.5` is a double and `x` is an int. <br />

Now what happens when something does not line up? We call `typeError()`:

```c++
static void typeError(TypeChecker* checker, ASTparser* parser, Expr* expr, const char* message, const char* messageType)
{
    if (parser->panicMode) return;

    fprintf(stderr, ":>>  | %s | at line %d: %s] \n", messageType, expr->line, message);
    checker->hadError = true;
    checker->errorCount++;

    parser->hadError = true;
    parser->panicMode = true;
}
```
*Found in /src/typeChecker.c*

It prints the error, using the line number that every node stores (this is why each `Expr` has a `line`), and sets `hadError` so the program never gets to run. Just like on the AST page, it also sets `panicMode`, and here it is doing something really useful. When a child comes back as `VALUE_ERROR`, its parent can't make sense of it either, and would happily report a second, nonsense error on top of the first one. `panicMode` swallows everything after the first error, so bogus errors aren't shown to the user, scaring them off or annoying them. Here is what any given one error looks like:

```
:>>  | TYPE ERROR | at line 2: If you want to do math, you have to use numbers (double, float, int), please.]
```

Arrays follow the same pattern. The type of an array like `[1, 2, 3]` is worked out from its first element, and every other element has to match it:

The result is the array version of that type, so `[1, 2, 3]` is an `int[]`. Indexing into an array needs an `int`, and `&&` and `||` need a `bool` on both sides, in the same way. <br />

There is one case that we skipped, `EXPR_VARIABLE`. All the tree gives us for a variable is its *name*, like `x`. Nothing about the tree says what type `x` is. So where does the checker find out? That is what the symbol table is for.

# The Symbol Table

Here is the problem. The AST compiler builds, and the type checker checks, **one expression at a time**, and then the tree gets freed. By the time we get to `x + 1`, the tree for `make int x = 5;` is long gone. <br />

So the checker has to remember. It keeps a **symbol table**, which is a list of every name that the program has declared so far, along with what each of them is. Anything that has to outlive a single expression lives in here.

```c++
typedef struct
{
    const char* name;
    int length;
    ValueType   type;
    int depth;

    //for actual functions and the temp for native initialization
    ObjFunction* function;
    bool isTemp;

    //for classes
    const char* className;
    int classNameLength;
    const char* superClassName;
    int superClassNameLength;

    //for class instances
    CheckerFieldInfo* fieldsInfo;
    int fieldCount;
    int fieldCapacity;

    //for class methods
    CheckerMethodInfo* methodInfo;
    int methodCount;
    int methodCapcaity;
} Symbol;
```


A `Symbol` is one entry in the table. The basics are the `name`, the `type`, and the `depth`, which is how deep in scopes it was declared (the same idea as on the `Local` struct from the AST page). Everything else is extra information for functions, classes, and instances, and we will get to those in part three. <br />

The `TypeChecker` struct holds the table itself, which is just a flat array of symbols with a count, `varCount`. It is capped at `MAX_SYMBOLS` (4096). It also holds the error flags, and a couple of class names that we will see later on. <br />

There are really only two operations on the table:

```c++
Symbol* lookUpSymbol(TypeChecker* checker, const char* name, int length)
{
    for (int i = checker->varCount - 1; i >= 0; i--)
    {
        if (checker->symbols[i].length == length &&
            memcmp(checker->symbols[i].name, name, length) == 0)
            return &checker->symbols[i];
    }
    return NULL;
}
```

```c++
void addSymbol(TypeChecker* checker, const char* name, int length, int depth, ValueType type, ObjFunction* function, ASTparser* parser)
{
    if (checker->varCount >= MAX_SYMBOLS)
    {
        error("Too many variables have been declared.", "MEMORY ERROR", parser);
        return;
    }
    int index = checker->varCount++;
    checker->symbols[index].type = type;
    checker->symbols[index].name = name;
    checker->symbols[index].length = length;
    checker->symbols[index].depth = depth;
    checker->symbols[index].function = function;
    checker->symbols[index].isTemp = false;
    checker->symbols[index].className = NULL;
    checker->symbols[index].classNameLength = 0;
    checker->symbols[index].superClassName = NULL;
    checker->symbols[index].superClassNameLength = 0;
    checker->symbols[index].fieldsInfo = NULL;
    checker->symbols[index].fieldCount = 0;
    checker->symbols[index].fieldCapacity = 0;
    checker->symbols[index].methodInfo = NULL;
    checker->symbols[index].methodCount = 0;
    checker->symbols[index].methodCapcaity = 0;
}
```
*Found in /src/typeChecker.c*

`addSymbol()` pushes a new symbol onto the end of the array, and `lookUpSymbol()` searches the array **backwards**, from the newest symbol to the oldest. That makes the table basically a stack with a linear search. Searching newest first is what makes shadowing work. So basically the same way we have it set up in the ASTCompiler with the compiler struct. If an inner scope declares a new `x`, it is the newest entry, so it gets found first, and the outer `x` is left untouched underneath it. This code prints `inner` and then `2`:

```java
make int x = 1;
{
    make string x = "inner";
    println(x);
}
println(x + 1);
```

Now, a linear search is technically not the fastest way we can look up symbols, a hashmap is. However, a direct linear search is very simple to implement for one, and God knows I was out of my mind writing this so it helped, but keep in mind all of this also happens during compilation. Hence a linear search here does not outright hurt the actual performance of the language, only the time it takes to compile. <br />

`checkVariable()` is about as simple as it gets. Look up the name, and give back the type that is stored there, or report an `UNDEFINED ERROR` if it was never declared. Assigning to a variable is only slightly more work. We look it up, check the type of the new value, and the two have to match exactly:

So who is putting all of these symbols in the table? The checker owns it, but it is the AST compiler that writes to it. `varDeclaration()` adds every variable (globals at depth `0`, locals at whatever depth they are declared at), `functionDeclaration()` adds the parameters of a function, the first pass adds functions and classes, and `#pullf` adds natives. <br />

And who takes them back out? When a scope ends, `endScope()` pops the symbols too:

```c++
    //pop in tandem with symbol table
    while (checker->varCount > 0 &&
       checker->symbols[checker->varCount - 1].depth > compiler->scopeDepth)
    {
        checker->varCount--;
    }
```
*Found in /src/ASTcompiler.c (trimmed, inside endScope())*

Anything that was declared deeper than the scope we are returning to just gets popped off the end by lowering `varCount`. Nothing is freed, the entries are simply forgotten, which is exactly how a stack should behave. <br />

It is the same job as the `locals` array in the `AstCompiler`, and the two are popped together on purpose (look at the comment, "pop in tandem"). They just answer different questions. The compiler's `locals` array knows **where a variable lives** (its slot on the stack), and the checker's symbol table knows **what it is** (its type). The bytecode compiler needs the first one, and the type checker needs the second.

# Functions, Natives, and Classes

So far a symbol has been a variable with a type. The same table also holds functions, native functions, and classes, which is what all of those extra fields on `Symbol` are for. This is where most of the type checker's code lives (the `EXPR_CALL` case alone is about 300 lines), but the idea is the same everywhere: look something up in the table, and then compare what you were given to what it says.

## Functions

A function is a symbol whose `function` field points at an `ObjFunction`, which is the very same object that the VM ends up running. The checker only cares about its **signature**: the `arity`, the `returnType`, and a list of `params`, each of which holds a type, a name, and whether it `isOptional`. <br />

There is a catch though. The checker needs a function's signature when it sees a *call* to it, and that call could come before the function has been compiled, or even before it is declared. This is exactly what the first pass of the [two pass compile](https://olinat.net/docs/system-design/astCompiler) is for:

```c++

                    //...
```

During the first pass, `declareFunction()` reads only the signature of each function. It builds a temporary `ObjFunction` to hold it, and adds it to the symbol table, skipping the body. Then in the second pass, when the real function gets compiled, `functionDeclaration()` swaps the temporary signature out for the real one:

```c++
    Symbol* existingSymbol = lookUpSymbol(checker, name, nameLength);
    if (existingSymbol) { existingSymbol->function = function; }  // Replace placeholder with real function
```
*Found in /src/ASTcompiler.c (trimmed, inside functionDeclaration())*

The payoff is that a function can call another one declared further down the file, because by the time its body is being compiled, the checker already knows what the other function looks like. <br />

*Cool Note:* That is only half of the story. The checker knowing about a function does not mean the VM has defined it yet, since the VM still defines functions in order as the program runs. So calling a function from the top level of your program, on a line before the one that defines it, still fails at runtime with an undefined global. Calls from inside of other functions are fine though, because those don't run until everything has been defined. <br />

Now for actually checking a call. Calls are `EXPR_CALL` nodes, and this is how a plain function call goes:


First we look the name up, and if nothing is found, that is an `UNDEFINED ERROR`. (Trying to call something that isn't a function, like calling an `int` variable, ends up here too, since that symbol has no `function`.) <br />

Then we check the **count**. Any parameter that isn't `isOptional` is required, so the number of arguments has to land between the number of required parameters and the total. After that we check each argument, by calling `checkExpression()` on it, which is the recursion again, and compare the result with the type that parameter expects. If it all matches, the type of the entire call is just the function's `returnType`. <br />

You might have noticed the `VALUE_ANY` types sneaking into the middle of that check, and the three `continue`s that skip the exact comparison. Those are for the next section.

## Natives

Native functions are the standard library functions that are written in C, like `println` or `sqrt`. The type checker has no idea how a native works, and it doesn't need to. To the checker, a native is just a function with a name, some parameters, and a return type. So to type check natives, all we do is add a symbol for each one:

```c++
static void registerNativeSymbol(TypeChecker* checker, const char* name, int length, ValueType returnType, ParamInfo* params, int paramCount, ASTparser* parser, struct Vm* vm)
{
    // create a dummy ObjFunction just to hold the signature
    ObjFunction* sig = calloc(1, sizeof(ObjFunction));
    sig->returnType = returnType;
    sig->arity = paramCount;
    for (int i = 0; i < paramCount; i++)
    {
        sig->params[i] = params[i];
    }
    addSymbol(checker, name, length, 0, returnType, sig, parser);
    checker->symbols[checker->varCount - 1].isTemp = true; //for freeing later so no memory leaks out
}
```
*Found in /src/typeChecker.c*

We make a dummy `ObjFunction` just to hold the signature (with plain `calloc`, since it is not a real VM object and never gets run), fill it in, and add it to the table at depth `0`. The `isTemp` flag lets `freeTypeChecker()` know to free it once compiling is done. <br />

Every library has a function like this one that registers all of its functions in bulk:

```c++
void registerIOSymbols(TypeChecker* checker, struct ASTparser* parser, struct Vm* vm)
```

These are called by the AST compiler whenever it meets a `#pullf`, which you can see more of in [#pullf and Natives](https://olinat.net/docs/system-design/astCompiler). This is only the type checker's half of registering a library. The other half, `registerXNatives()`, gives the VM the actual C functions, and you can read about it on the [Functions & Natives](https://olinat.net/docs/system-design/functions) page. Libraries are opt-in, so if you never `#pullf` one, its symbols never get added, and calling any of its functions is an `UNDEFINED ERROR`. <br />

Now we can finally explain `VALUE_ANY`. `println` accepts a value of any type, `sqrt` accepts any number (an `int`, a `float` or a `double`), and `length` accepts any array. The functions you write yourself can't do that, since every parameter has to be one exact type, so these three special types exist only so natives can be a little more flexible. Those are the `continue`s from the call check, and they are what give you errors like these:

```
:>>  | TYPE ERROR | at line 2: Please only input numeric arguements (int, float, double)]
:>>  | TYPE ERROR | at line 2: Please input an array as an arguement into this function.]
```

That `isOptional` is the same idea. You can see it on `intake` above, where the prompt is optional, so both `intake()` and `intake("Name: ")` pass the check. <br />

*Cool Note:* Adding a function to the standard library means touching **both halves**. You write the function in C for the VM, and then you add a `registerNativeSymbol()` line for the type checker. Forget the second half, and the function exists at runtime, but the checker has never heard of it, so no program can call it. The [Project Structure](https://olinat.net/docs/contributing/project-structure) page lists where each of those pieces lives.

## Classes

Classes are the most complicated part of the type checker. A class isn't a single type, it is a whole collection of fields and methods, and every instance of it has to be checked against that collection. It is all built on the same symbol table though, so nothing here will be new, there is just more of it. <br />

Just like functions, classes are written down during the first pass. A class becomes a symbol with the type `VALUE_CLASS`, and its fields and methods are stored right inside of that symbol:

The class symbol gets a `superClassName` if it inherits from something, a growing array of `fieldsInfo` (a name and a type for each field), and a growing array of `methodInfo` (a name, a return type, and a parameter list, exactly like a function). <br />

Now for an interesting detail about how types work here. Every instance, no matter which class it came from, has the same type in the enum, `VALUE_INSTANCE`. There is no separate "Player type" and "Enemy type". So the checker keeps track of *which* class an instance is on the side. When you write `make Player p = Player();`, the variable's symbol gets a `className`:


Where does `checker->lastClassName` come from? It is a little breadcrumb that the checker leaves for itself. Writing a class name as a type (`make Player ...`) leaves one, and so does calling a class (`Player()`). Then `varDeclaration()` copies the latest breadcrumb onto the new variable's symbol. Now `p` is a `VALUE_INSTANCE` with the `className` of `Player`. <br />

If the thing being called is a `VALUE_CLASS`, we leave the breadcrumb, check any arguments against the class's constructor (the method with the same name as the class), and say that the result is a `VALUE_INSTANCE`. <br />

Next up is getting at an instance's fields, like `p.hp`. This is `checkClassField()`, and it handles both reading and writing a field:

We search the fields of that class, and if the field isn't there, we walk **up the chain of superclasses** using `superClassName`, searching each parent in turn. That is how a child class can use the fields that it inherited. If we run out of classes without a match, it is an `Undefined field` error. <br />

Calling a method, like `p.heal(5)`, goes down the very same road. It is an `EXPR_CALL` whose callee is a field access, so we find the class the same way, and then search `methodInfo` instead of `fieldsInfo`:

Two more keywords need to know about classes. `this` is the easy one, because we already know the class: it is `currentClassName`, which the AST compiler sets while it is compiling the body of a class. Outside of a class, it is an error.

*Cool Note:* Since the class of an instance is remembered by the variable's symbol (and that breadcrumb), it only works when there is a variable to look at. That is the reason for a few quirks you might run into. An instance passed into a function as a parameter doesn't remember its class, so `p.hp` inside of that function is an `Unknown class type` error. An instance inside of an array doesn't remember it either, so `team[0].hp` doesn't work. And because every instance is just a `VALUE_INSTANCE`, `make Player p = Enemy();` currently slips through the checker, and `p` simply gets treated as an `Enemy`. A real fix would be to make the class a proper part of the type, and that would be a great first contribution for anybody who wants to dig into the checker.

# Where to Go Next

That is the type checker! Every tree that the AST compiler builds gets walked, one expression at a time, and either comes back with a type, or the program stops right there with an error. Once a tree gets its stamp of approval, it moves on to the [ByteCode Compiler](https://olinat.net/docs/system-design/bytecodeCompiler), which turns it into the instructions that the VM runs.
